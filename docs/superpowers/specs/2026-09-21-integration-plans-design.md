# 海岸与山野对接计划文档设计

## 目标

建立一套可分阶段评审、可独立验收、可按依赖顺序执行的 iOS 对接计划文档，用于将现有「海岸与山野」UIKit 本地应用与远程配置、加密 API、快捷登录、业务 H5、JS Bridge、IAP 及归因能力对接。

计划只覆盖合法、可如实提交 App Store 审核的产品能力，不设计或实施向审核人员隐藏真实功能的界面切换、审核绕过或误导性远程开关。

## 现状与边界

现有工程已包含原生探索、学习、出游、装备、手记、收藏、提醒、个人中心、本地账号、隐私同意、本地数据导出和清除。现有 `LearningWebController` 用于本地学习文章，不视为业务 H5 容器。

本轮文档工作不修改业务代码，不接入 SDK，不改动 Bundle ID、签名、权限或发布配置。

## 文档组织

计划文档统一存放在 `docs/integration-plans/`，包含一份总计划和十三份专项计划：

1. `00-对接总计划.md`
2. `01-环境配置与发布配置计划.md`
3. `02-通信加解密模块计划.md`
4. `03-网络层与API对接计划.md`
5. `04-远程登录与账号迁移计划.md`
6. `05-账号注销与隐私合规计划.md`
7. `06-业务WebView容器计划.md`
8. `07-JS-Bridge对接计划.md`
9. `08-IAP内购与权益计划.md`
10. `09-归因与埋点计划.md`
11. `10-UGC与内容安全计划.md`
12. `11-测试与验收计划.md`
13. `12-App-Store提审计划.md`
14. `13-上线监控与回滚计划.md`

`00` 管理整体范围、阶段门禁、依赖和验收状态。`01`—`09` 是工程实现计划，`10` 是条件性计划，`11`—`13` 是质量、发布和运营保障计划。

## 文档统一结构

每份专项计划使用相同的结构：

- 目标与非目标。
- 当前工程证据和差距。
- 前置依赖、外部输入和决策门禁。
- 将新建或修改的精确文件。
- 模块接口、数据流与错误边界。
- 以失败测试开始的小步实施任务。
- 每个任务的精确执行命令和预期结果。
- 安全、隐私、审核和回滚注意事项。
- 可量化验收标准和完成定义。

任务步骤使用 Markdown 复选框，为后续执行和复核保留进度。计划不包含 `TBD`、`TODO` 或「视情况处理」等无法验收的占位描述。

## 总体架构原则

- 保留现有 UIKit 原生功能，不将应用降级为简单网页套壳。
- 对接能力拆分为配置、密码学、网络、身份、Web、Bridge、支付和归因模块。
- 原生学习文章 WebView 与远程业务 WebView 保持独立，避免安全策略、消息处理器和 Cookie 状态相互污染。
- 远程账号与现有本地账号不默认合并，必须在账号计划中明确迁移或并存规则。
- IAP 以服务端验单成功作为发放权益的最终依据。
- 归因与非必要 SDK 必须延后到用户隐私选择之后初始化。
- 正式环境优先 HTTPS，不使用全局 ATS 放开作为默认方案。

## 执行依赖

主顺序为：

`01 → 02 → 03 → 04 → 05 → 06 → 07 → 08 → 09 → 11 → 12 → 13`

`10` 只在产品开放公开作品、评论、用户资料、消息或公开 AI 内容时进入实施主线。

`02` 和 `01` 完成后，`03` 才可开始。`06` 依赖 `04` 产出可注入的会话与配置数据。`07` 依赖 `06` 的 WebView 容器。`08` 依赖 `03`、`04` 和 `07`。`09` 依赖用户同意模型、服务端配置和上报 API。

## 计划中不预设的外部值

正式域名、API 混淆路径、App Store ID、Adjust Token、Facebook 参数、IAP SKU、隐私政策 URL 和服务条款 URL 必须来自项目正式配置，不从示例工程复制。

计划会将这些值标记为「实施前必须提供的外部输入」，而不是代码或文档中的占位字符串。

## 验收标准

- 十四份文档均存在，命名、编号和依赖一致。
- 每份实施计划列出精确文件、接口、测试命令、预期结果和验收条件。
- 所有需求均能追溯到一个明确任务，不存在未分配的功能。
- 不将文档中的审核规避描述转化为实施任务。
- 不把公开 UGC、AI、IAP 或归因默认为已确定的产品范围；条件不成立时可整体跳过对应计划。
- 计划本身不改动现有用户未提交代码。
